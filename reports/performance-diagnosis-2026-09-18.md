# 2026-09-18 학생 태블릿 입력·스크롤 끊김 점검

학생 브라우저의 입력 경로에 반복적인 본문 변환, 넓은 화면 갱신, 수업 자료 전체 저장이 확인됐다. 현재 서버의 CPU·메모리 과부하를 주원인으로 지목할 증거는 부족하다. 일부 학생의 연결 실패도 따로 확인됐다. 학생 태블릿의 성능 기록을 직접 얻은 것은 아니므로 실제 끊김의 단일 원인을 확정하지 않는다.

제품 코드·운영 서버·수업 데이터는 변경하지 않았다. 운영 수업에 시험 참가자를 넣거나 새로고침하지 않았다. 점검 파일과 별도 임시 브라우저만 사용했으며 시험 서버·브라우저는 종료했다.

## 운영 상태

- 점검 중 `/api/health`: 정상, 방 1개, WebSocket 23개, 로그 저장 정상. 연결 수는 해당 순간의 소켓 수이며 정상적으로 글을 쓰는 학생 수가 아니다.
- 운영 Node 서버(PID 3380): working set 약 49.5 MiB. Cloudflared(PID 4272): 약 49.8 MiB. 다른 시점의 private working set은 각각 23.4 MiB, 26.0 MiB였다.
- Windows 성능 카운터의 두 프로세스 CPU는 각각 4% processor time으로 관측됐다. 논리 프로세서 4개인 이 PC의 전체 처리 능력 기준으로 각각 약 1%에 해당하는 짧은 표본이다. 장기 최대 사용량을 뜻하지 않는다.
- PC 전체 메모리 15.75 GiB 중 여유 2.46 GiB. 짧은 디스크 표본의 대기열은 0이었다. 이 수치는 원격 학생 태블릿의 메모리·디스크 상태를 나타내지 않는다.
- 배포 자산 `dist/assets/index-CrdtfgNZ.js`에서도 트랜잭션마다 재렌더링, `getHTML()`, `gc:false` 설정을 확인했다. 소스 실험과 운영 번들 전체가 동일하다고 검증한 것은 아니다.

## 우선 확인·개선할 부분

### 1. 매 입력 때 본문 전체를 두 경로에서 변환한다 — CPU

`src/classroom.ts:1409`의 Yjs update 콜백이 매번 `project()`를 호출한다. `src/classroom.ts:1434`의 `project()`는 Yjs 본문 전체를 ProseMirror 문서로 만들고, 별도 DOM으로 직렬화한 뒤 HTML을 정화하고 전체 텍스트·피드백 위치를 계산한다.

동시에 `src/WritingEditor.tsx:124`는 `getHTML()`과 `getText()`로 같은 본문을 다시 변환해 `onUpdate()`로 전달한다. 실제 수업의 `updateDoc()`는 본문을 Yjs가 처리하므로 이 HTML·paragraphs를 사용하지 않는다. 실제 수업 모드에서 이 중복 변환을 생략하는 것이 가장 명확한 첫 개선이다. 미리보기 등 비협업 모드에는 기존 갱신이 필요하다.

문서 요약·읽기용 HTML 생성은 필요한 화면에서만 하거나 여러 입력을 모아 처리하는 방향이 적절하다. 편집·동기화 원문 자체를 지연시키는 것과 구분해야 한다.

### 2. 입력·저장 상태가 상위 화면까지 갱신된다 — CPU와 렌더링

`src/WritingEditor.tsx:102`의 `shouldRerenderOnTransaction: true`는 편집 트랜잭션마다 React 편집기 렌더링을 요청한다. `src/classroom.ts:356`은 모든 Yjs 변경에 `emit()`을 호출하고, `src/App.tsx:51`은 수업 상태 전체를 구독한다. 저장 완료도 상태를 갱신한다. 따라서 본문 외에 도구막대, 글자 수, 저장 표시 등을 함께 다시 계산한다.

분리 시험에서 입력 30회에 상위 글쓰기 화면은 61회 렌더링됐다. 이는 시험용 구독 컴포넌트의 수치이며 운영 App 전체의 실측 렌더 횟수는 아니다. 필요한 상태만 구독하고 도구막대·글자 수·저장 표시를 분리하는 개선이 우선이다. [Tiptap 공식 성능 안내](https://tiptap.dev/docs/guides/performance)도 과도한 React 재렌더링과 해당 옵션의 제어를 설명한다.

### 3. 입력이 120ms 쉬면 수업 자료 전체를 복제·저장한다 — CPU, 메모리 할당, 저장 I/O

`src/classroom.ts:360`은 마지막 변경 120ms 뒤 `flush()`를 실행한다. 매 120ms의 고정 주기 저장은 아니며 변경이 이어지면 타이머가 미뤄진다. 다만 120ms보다 긴 입력 간격에서는 거의 입력마다 저장할 수 있다.

`src/classroom.ts:388`은 lesson 전체를 `structuredClone()`하고, 보유한 모든 문서를 `Y.encodeStateAsUpdate()`로 인코딩해 IndexedDB에 넣는다. 학생 쪽은 자기 원고뿐 아니라 이미 받은 게시글·댓글·자료도 lesson에 포함한다. 호스트는 반 전체 문서를 보유한다. 저장 요청은 직렬로 실행되지만 복제와 인코딩은 대기열에 넣기 전에 실행된다.

변경 문서 단위 저장, 공개 게시판 자료와 원고의 저장 분리, 저장 중 쌓인 요청 병합을 검토할 필요가 있다. 저장 주기를 바꾸더라도 페이지 이탈·게시·교사 작업의 저장 보장은 유지해야 한다.

### 4. 게시·댓글 등은 게시판 전체를 다시 보내고 재처리한다 — 네트워크, CPU, 저장 I/O

`src/classroom.ts:1278`의 `sendSnapshot()`은 공개 게시글·댓글·자료 전체를 포함한다. 게시판 행동이나 접속 상태 변화가 `changed()`를 호출하면 준비된 각 참가자에게 전송한다. 수신 기기는 `src/classroom.ts:1369`에서 lesson을 교체하고 자기 문서를 다시 `project()`한 뒤 저장한다. 게시판 카드도 `src/ui.tsx:137`에서 HTML 정화를 거쳐 렌더링한다.

학생이 쓰는 중에도 다른 학생들의 게시·댓글 동작이 몰리면 이 작업이 겹칠 수 있다. 실제 이번 수업의 게시글 수·본문량·게시판 메시지 빈도는 수집하지 않았다. 본문 타이핑 자체는 `changed(false)`와 Yjs 증분 동기화 경로이므로, 글자 하나마다 모든 학생에게 전체 게시판이 전달된다고 해석하면 안 된다.

### 그 밖의 후보

- `src/classroom.ts:1406`의 Yjs `gc:false`는 삭제된 편집 정보가 오래 남는 방향이다. 장시간 편집 시 비용이 늘 수 있지만 이번에 태블릿 메모리 증가나 누수를 측정하지 않았다. 피드백 위치·실행 취소와 관계가 있으므로 무작정 켜고 끌 대상은 아니다.
- 진단 기록은 최근 최대 1,000건을 JSON으로 만들어 sessionStorage에 동기 저장한다(`src/diagnostics.ts:36`). 연결 오류가 몰리는 기기에는 추가 부담이 될 수 있다. 정상 입력마다 진단을 쓰는 구조는 아니며 이번 시험의 주병목으로 확인하지 않았다.

## 분리 시험

`.deploy/performance-probe-2026-09-18.mjs`에서 현재 앱 소스의 Classroom, WritingPage, WritingEditor를 production 모드로 별도 번들링했다. 임시 로컬 서버와 새 headless Chrome 저장소에 가상 원고만 생성했고 실제 서버·학생 데이터는 사용하지 않았다. 시험은 한 브라우저씩 순서대로 실행했다.

입력 간격 150ms로 30회 `insertContent()`를 호출했다. 마지막에 명시적 flush 1회를 수행했다. 따라서 아래 31회 저장에는 마지막 flush가 포함된다. 네트워크·한국어 IME 조합·실제 터치 스크롤·앱 CSS 레이아웃·전체 App 화면은 재현하지 않았다. CPU 4배 제한은 느린 CPU 조건의 모의 시험이며 학생 기종을 재현한 값이 아니다.

## 별도로 확인한 연결 문제

운영 `logs/doto.jsonl`의 서버 수신 시각 2026-09-18 11:48:37.742~11:58:37.742(UTC+9)에서 브라우저 eventId 중복을 제거한 558건을 분석했다.

- 요청 시간 초과 6건, 서버 heartbeat timeout 2건, 브라우저 socket.error 3건, 수업 오류 9건이 있었다. 수업 오류 원문이나 작업 종류를 기록하지 않으므로 모두 입력 렉이라고 단정하지 않는다.
- 같은 구간의 browser.error / browser.rejection / storage.failed는 0건이다. 오류 로그가 없다는 사실이 기기가 부드럽게 동작했다는 뜻은 아니다.
- RTC 통계 38건에서 RTT 중앙값 21ms, p95 143ms, 최대 154ms였다. 송신 대기 메시지는 표본상 모두 0개였지만 DataChannel bufferedAmount는 최대 101,603바이트였다.
- 이 RTC 통계는 **직접 연결 한 쌍의 양쪽 브라우저**에서 나온 값이다. 중계 연결을 포함한 전체 학생망이 정상이라고 일반화할 수 없다. 현재 로그에는 중계 경로의 지연·전송량과 브라우저 CPU·프레임·입력 지연이 없다.

## 판단과 다음 확인

우선순위는 실제 수업 모드의 불필요한 HTML 변환 제거 → 편집기와 앱 상태 구독 범위 축소 → 변경 문서 중심 저장 → 게시판 변경분 전송이다. 실제 학생 기기에서 성능 기록을 얻어 긴 작업, 렌더링, 한국어 조합 입력, GC 중 어느 구간이 끊기는지 대조하면 원인을 확정할 수 있다.
