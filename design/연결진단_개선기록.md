# 연결 진단 개선 · 2026-09-07

사용 증상은 서로 다른 인터넷망의 교사 PC와 Android 태블릿 사이에서 학생이 “선생님과 연결하는 중이에요…”에 머문 뒤 연결이 끊기는 현상이다.

## 기존 기록에서 확인한 범위

- `.doto.log`에는 서버 시작 기록 3줄만 있었다. 입장·신호·ICE·DataChannel 오류 기록은 없었다.
- `.ui-preview.log`는 시안 개발 서버 기록으로, 문제의 실제 수업 연결 원인을 확인할 자료가 아니었다.
- 점검 시 로컬 주소와 사용자 제공 외부 호스트의 `/api/health`가 모두 응답했다. 설정은 STUN 하나를 사용하는 직접 연결이었다.
- 과거 실패의 정확한 원인은 확정하지 못했다. Android 실기기와 서로 다른 망에서 새 기록으로 다시 확인해야 한다.

## 변경

- 서버와 브라우저의 연결 메타데이터를 `logs/doto.jsonl`에 저장한다. 시각, 브라우저·시도·요청 ID로 양쪽 기록을 연결한다.
- 방 생성/입장/교사 부재, 신호 송수신/누락/거절, WebSocket 종료·하트비트 실패, ICE 후보 종류/개수/오류, 연결 단계, DataChannel, 대기 초과, 네트워크·페이지 상태, 저장 실패를 기록한다.
- 브라우저 업로드가 실패하면 해당 탭에 제한된 기록을 보관하고 재전송한다. 실패 화면과 교사 설정에서 진단 기록을 파일로 저장할 수 있다.
- 허용 필드만 기록한다. 이름, 입장 코드, 토큰, 학생 글, 메시지, 원본 SDP·후보 주소와 오류 원문은 제외한다.
- 로그 파일은 기본 약 25 MiB 이내에서 순환한다. Docker 재생성에도 남도록 볼륨을 추가했다. 수집 여부와 쓰기 상태는 `/api/health`에서 확인한다.
- ICE 후보가 offer보다 먼저 왔을 때 기존 peer를 교체하며 후보를 버리는 경로를 고쳤다. 비동기 SDP/ICE 처리를 도착 순서대로 수행한다. 이 코드 결함이 사용자 현상의 실제 원인이었는지는 아직 확인되지 않았다.
- 설정 요청에도 시간 제한을 적용하고 DataChannel이 열리기 전 연결 준비 제한 시간이 해제되지 않게 했다.

## 검증

- 빌드·TypeScript 검사 통과.
- Node 진단 검사 4개 통과: 필드 필터, 파일 순환/재시작, 업로드 검증, 저장 경로 장애.
- 기존 신호 서버 검사 통과: 역할·신호 제한, 입장 잠금, 학생/교사 재입장 등.
- 기존 수업 흐름 브라우저 검사 2개 통과: localhost와 HTTP 일반 호스트에서 교사·학생 협업, 메시지·게시·재입장·보관.
- 최종 진단 브라우저 검사 6개 통과: 두 호스트 각각에서 후보 선도착/끊김/재접속/파일 저장, 업로드 실패 후 새로고침·재전송, 20초 대기 초과.

실행 중인 이전 서버에 적용하려면 서버 재시작과 교사·학생 화면 새로고침이 필요하다. 서버의 방 정보는 메모리에 있으므로 재시작 후 입장 코드가 바뀔 수 있다. 학생 글은 기존과 같이 각 브라우저에 보관한다.

## 재시작 뒤 실제 접속 기록

2026-09-07 10:35~10:36 (UTC+9)의 두 번의 학생 접속에서 다음을 확인했다.

- 서버의 진단 기록 쓰기와 학생 브라우저 로그 업로드가 정상이다.
- 입장, 교사 offer, 학생 answer, 양방향 ICE 후보 전달이 성공했다.
- 학생은 host 후보 2개와 srflx 후보 2개를 얻었다. 교사에게서는 후보 2개를 받았다.
- 학생의 연결 상태는 checking/connecting에 머물다가 약 15초 뒤 failed로 바뀌었다. DataChannel은 열리지 않았다.
- 교사 요청에는 새 진단 버전이 붙이는 clientId/attemptId가 없고 교사 브라우저 진단도 없었다. 교사 탭은 이전 코드를 실행 중인 것으로 보이며, 강력 새로고침 후 양쪽 기록을 다시 확인해야 한다.
- 앞선 10:31의 실패는 invalid-code였지만 10:35 이후 입장은 성공했다. 두 실패를 구분해야 한다.

같은 PC의 별도 Chrome 검사에서는 host와 srflx 후보를 얻었다. 이것만으로 실제 교사 탭의 브라우저 정책이나 두 망 사이의 직접 연결 가능성을 확인한 것은 아니다.

종료 직후 getStats 결과가 비어 나오는 한계가 있어 준비 중 5초 간격으로 통계를 남기고, 받은 상대 후보 종류도 기록하도록 추가 보강했다. 이미 종료된 연결에서 얻은 결과는 성공적인 빈 통계로 취급하지 않는다. 이 추가 변경은 브라우저 코드에만 있으므로 서버 재시작 없이 화면 새로고침으로 적용한다.
